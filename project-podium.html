Product Context

Replacing scattered match records with one shared system

Commander groups often rely on memory, notes, or spreadsheets to track games. Those methods become difficult to maintain once players rotate, decks change, and a group wants to compare performance over time.

Podium brings that activity into one responsive product. Players can manage playgroups, decks, commanders, and card collections, log sessions, and review personal or group-level statistics without rebuilding the same context after every game night.

The Challenge

Make structured tracking feel lighter than a spreadsheet

The product needed enough structure to generate trustworthy statistics without slowing down the social setting it was designed for. Every extra field could improve the data while also making the app less convenient to use at the table.

01

Fast At The Table

Reduce repeated setup and keep the session form focused on information that affects the final record.

02

Flexible Groups

Support different pod sizes, team formats, recurring players, and changing deck choices without losing session history.

03

Useful Statistics

Turn recorded results into readable comparisons across commanders, decks, game formats, pod sizes, and recent form.

Core Product Loop

From joining a pod to learning from the result

I structured Podium around a repeatable loop that keeps setup separate from the actions needed during a game night. Once players and decks exist, each new session becomes faster to record.

  1. 01

    Open A Playgroup

    Choose a playgroup and review its recent sessions before recording another match.

  2. 02

    Select Players

    Add the participants involved in the session and keep each result tied to the correct player.

  3. 03

    Choose A Deck

    Select a saved deck or commander so each result retains meaningful context.

  4. 04

    Log The Game

    Record players, format, result, and optional details through one focused session form.

  5. 05

    Review The Data

    See personal and group trends update from the newly recorded session.

UX Decisions

Designing around real game-night tasks

The interface prioritises frequent actions and separates them from deeper analysis. Session logging uses a wide, structured form on desktop, while dashboards surface recent activity and quick actions before detailed statistics.

Progressive Detail

Common summaries appear first, while deeper breakdowns remain available when a player wants to investigate.

Persistent Context

Players, pods, decks, and commanders are connected so repeat sessions require less manual entry.

Scannable Results

Tables, cards, and charts give different kinds of data a consistent hierarchy across the product.

Product System

Connecting decks, card data, and group history

Podium grew from a session tracker into a broader Commander library. Deck and commander records enrich each match, while Scryfall-backed card data helps players search, inspect, and organise the cards connected to their decks.

The same underlying session data can then support personal dashboards and deeper group comparisons without asking users to enter the result more than once.

Development & Iteration

Learning React through a product that kept growing

Podium was my first large React product. Building a real application rather than a small exercise meant learning component structure, state, dynamic forms, conditional interfaces, and reusable patterns while the feature set was actively expanding.

I designed the interface directly in React rather than creating a separate Figma prototype. Working in the browser let me evaluate layout, responsive behaviour, interaction states, and technical constraints together, then refine each workflow in the functioning product.

Firebase permissions became part of the product architecture rather than a final technical task. Playgroup membership, deck visibility, and private session records required the data model and security rules to evolve together. Refactoring those early decisions taught me to plan ownership and access before adding another interface layer.

02

03

Ongoing Refactoring

New workflows exposed early assumptions, leading to iterative improvements in both the interface and application structure.

Outcome & Reflection

A live product and an ongoing design practice

Podium progressed from a three-month learning project into a deployed product that I continue to maintain. It demonstrates how I connect product thinking, interface design, data modelling, and frontend implementation across one evolving system.

The main lesson has been that iteration is not separate from design. Real workflows expose where terminology, hierarchy, permissions, and architecture need to change, and each release creates better evidence for the next decision.

Product Thinking

Raw match data only becomes useful when the product turns it into understandable decisions and comparisons.

System Design

Interface structure, data ownership, and security rules must support the same model of the product.

Continuous Improvement

The active product remains a place to refine workflows, visual consistency, performance, and responsive behaviour.
